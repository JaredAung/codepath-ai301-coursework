# Rubric: is this pull request ready to submit?

Grade the pull request against the plan it claims to implement and the
issue that plan belongs to. A disclosed shortfall can be ready. Less
than everything is a hold only when the shortfall is silent, or the
description claims the missing work is done.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | The diff's changed files and what each hunk changes, read against the plan's in-scope change, its not-in-scope line, and any deviation or deferral note. Then the description's fidelity sentences (what it says changed, and any "exactly the plan" or "no other changes" claim), read against that same diff. Locations: evidence guide, Plan fidelity. | The behavior in the diff is the plan's in-scope change. A test, changelog, or docs file the plan or the repo's template asks for, and a translated string for a message the plan adds, belong to that change. A new option, a file or rewrite the plan marks out of scope or never names, or a rename pass the plan does not name, fails unless a deviation note in the plan records that extra work. An in-scope deliverable missing from the diff fails, unless the plan's deviation or deferral note says this PR leaves it out and the description does not claim that deliverable is done. A description that claims a change the diff does not contain, or claims the diff is exactly the plan while it contains other behavior, fails. | required |
| test-decisive | The test-evidence section, read against every behavior the plan's test plan names, and against a test command the repo-facts block (eval) or `docs/CONTRIBUTING.md` (live) names. Locations: evidence guide, Test evidence. | For every behavior the test plan names and does not defer, the evidence shows the command or scenario and the observable outcome (output text, exit code, assertion, or a before and after). Evidence that only says the suite passed, that it works on one machine, or that shows the control path the repro says already succeeds, while the failing path is absent, fails. When the test plan names two failure modes, showing one fails. No test evidence fails. A deferred item named only in a deviation note is not required here. | required |
| diff-reviewable | The unified diff and the commit subjects, read for anything that is not the plan's change. Locations: evidence guide, Diff quality. | A reviewer can see the fix without reading past debris. Fail when the diff adds a debug print, a commented-out statement or earlier attempt, a function the diff marks unused or dead, a TODO on code the plan does not change, or a hunk that only reformats, rewraps, or reprints lines the plan does not change. An explanatory comment beside the fix, a test the plan asks for, and a changelog the template asks for pass. | required |
| template-honored | The description and, where the ask is a file, the diff, read against each concrete ask in the repo-facts pull-requests line (eval) or the PR template and `docs/CONTRIBUTING.md` (live). Locations: evidence guide, Standards and comms. | Each named section is filled with a sentence about this change, not left blank and not a copied placeholder. An issue-reference form the source requires (`closes #`, `fixes #`, or "reference the issue") appears with this issue's number. A file the source requires (whatsnew, CHANGELOG, changelog entry) is in the diff, unless the description says that item does not apply and why. When the source says there is no PR template, this check passes if the remaining asks that name an issue reference or a test file are met. "Stay small" is not failed here. | required |
| disclosure-present | The description, read against an AI-use rule in the repo-facts contribution policy (eval) or `docs/CONTRIBUTING.md` and any AI-policy file it points at (live). Locations: evidence guide, Standards and comms. | If that policy requires disclosing AI use (the tool, the extent, or that the words are the author's own), the description includes that disclosure. If the policy only says a human must understand the change, and it does not require a disclosure sentence, the check passes. If there is no AI policy, the check passes. A required disclosure that is absent fails even when the description never mentions AI. | required |
| thread-aware | The description, read against maintainer direction in the thread highlights (eval) or the issue thread (live): a member, owner, or maintainer naming a file, a forbidden API, a behavior to preserve, or an approach. Locations: evidence guide, Standards and comms. | If that direction is present, the description follows it or says why this PR does not. If the thread has no such direction, the check passes. A comment whose author is not a member, owner, or maintainer does not count. In live mode, a classmate's comment does not count. | required |

## Verdict rule

Accept (ready to submit) only when every check in the table is `pass`. Reject (hold) when any check is `fail` or `unclear`. Every check is `required`. A `preferred` check, if one is added later, is reported and never changes the verdict. `unclear` counts as `fail`.
